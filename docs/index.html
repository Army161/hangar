Three gates before anything dies

Hangar can stop processes. Every kill passes all three, in order.

1 — Dry run

Returns exactly what would die and what the guard refuses, with a confirmation phrase. Nothing is killed.

2 — Typed confirmation

Requires the plan id and the exact phrase. Plans are single-use and expire after five minutes.

3 — Re-evaluation

The guard runs again on a fresh process table. PIDs recycle, so a plan is a proposal, not a licence.

A restore manifest is written before the first kill. If the manifest cannot be written, nothing dies. Nothing is ever deleted — disabled startup entries move to quarantine/ and come back intact.

The views

Six answers to six different questions about your machine.

ViewWhat it answers
OwnersWhat is actually running, grouped by the real thing that owns it — not node.exe ×76.
Port wallEvery listening port, probed for HTTP and labelled with its page title.
OriginsEverything configured to start itself, oldest first, with the date it was added.
Fan-outThe same thing running more than once, and what collapsing it would reclaim.
GraveyardProjects that stopped being touched, ranked by what reviving or removing them reclaims.
ManifestsEvery park, newest first, with one-click Restore.

It never leaves the machine

The desktop build has no TCP listener at all — the UI talks to the Rust core over IPC. The web agent binds 127.0.0.1 only. There is no telemetry, no account, and no upload path. Your process table is yours.

Run with HANGAR_READONLY=1 to disable every write endpoint and use Hangar purely as an observer.
